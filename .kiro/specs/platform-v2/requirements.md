## 简介

### 产品定位

"营销任务平台"是面向 C 端用户的任务激励营销系统：运营人员在管理后台编排营销任务（步骤流程、参与条件、灰度放量、平台差异化动作），C 端用户在门户 H5 参与任务、按步骤完成，平台自动发放奖励（积分、优惠券、徽章等），并配套完整的系统管理、风控反作弊、数据埋点与运营位能力。

平台服务两类互不相通的账号体系：**后台管理账号**（运营/管理员）与**门户用户账号**（C 端），两者独立存储、独立认证、独立会话域。

### 用户角色

| 角色 | 使用端 | 职责 |
|------|--------|------|
| 系统管理员 | 管理后台 | 账号、角色权限、字典、系统配置、缓存治理、审计 |
| 运营人员 | 管理后台 | 任务编排、奖品与积分、广告位、看板分析、发放异常处理 |
| 风控人员 | 管理后台 | 名单管理、风控规则配置、风控事件处置 |
| C 端用户 | 门户 H5 | 注册登录与账号设置、浏览与领取任务、完成任务与放弃、领取奖品、查询积分、签到（P1）、浏览运营位 |
| 外部业务系统 | internal API | 回调任务步骤、上报任务进度（服务间签名调用，调用方登记制） |

### 应用与 API 命名空间规划

平台由两个独立部署的后端应用组成，接口命名空间从设计上支持网关按前缀静态路由与未来的模块级拆分扩展（新增独立模块集群时无需修改既有路由规则）：

| 命名空间 | 应用 | 说明 |
|----------|------|------|
| `/admin/**` | admin-app（管理应用） | 管理后台全部接口，含 `/admin/auth/**`、`/admin/captcha`、`/admin/simulate/**`（P1） |
| `/api/common/**` | portal-app（门户公共） | 门户公共服务，按业务模块细分第二段：`/api/common/auth/**`（认证）、`/api/common/task/**`（任务）、`/api/common/prize/**`（奖品）、`/api/common/points/**`（积分）、`/api/common/dict/**`（字典只读）、`/api/common/track/**`（埋点上报）、`/api/common/ad/**`（广告位，P1）、`/api/common/signin/**`（签到，P1）、`/api/common/captcha` |
| `/api/<module>/**` | 预留 | 未来从门户拆出独立部署的高流量或特殊模块（如 `/api/lottery/**` 抽奖活动），第二段即模块路由键，网关据此指向独立集群 |
| `/internal/**` | portal-app（初期） | 服务间内部接口，**不带 `/api` 前缀**，如 `/internal/task/callback`；网关按此前缀直接拦截公网访问 |

命名空间约束：

1. admin-app 只能暴露 `/admin/**` 与健康检查；portal-app 只能暴露 `/api/**` 与 `/internal/**`，两应用互斥，启动时校验（收到非本应用命名空间的请求一律 404）。
2. 门户业务接口一律挂在 `/api/common/<模块>` 下，禁止直接挂 `/api/<其他>`；新独立模块的启用是一次有意识的拆分决策（分配新的第二段前缀并独立部署）。
3. `/internal/**` 变更（新增/修改）必须同步更新网关拦截规则文档与全部已登记调用方。

### 不在范围内

支付、消息推送、短信通道、多租户、开放平台、积分商城消费场景、对外广告变现与第三方广告 SDK 对接（本平台"广告位"仅指自营运营素材投放位）、文件存储与图片上传能力（广告素材图片为运营方提供的外链 URL，平台仅存储引用）、埋点全埋点/可视化埋点（首版仅代码埋点与服务端事件）、匿名与登录身份的埋点归因打通（P1 评估）、**自助找回密码（首版无短信/邮件通道，门户与后台账号遗忘密码均由管理员人工重置，后台超级管理员遗忘由运维经环境变量重置初始密码后强制改密流程恢复）**、单点登录/外部用户中心对接（identity 预留扩展位）、真实第三方打款/渠道官方拉单（P0；有适配器再启用）。

## 用户故事与需求

### 模块 A：身份与权限

### 需求 1：后台账号登录

**用户故事：** 作为运营人员，我希望使用账号、密码与图形验证码登录管理后台，以便安全地访问与我职责匹配的管理功能。

#### 验收标准

1. 当用户提交正确的用户名、密码与有效验证码时，系统应在 2 秒内创建会话，经 `Set-Cookie` 下发会话（令牌不进 JSON，R1.13），响应体仅返回用户基本信息（昵称、角色、权限码集合）。
2. 当凭据任意一项错误时，系统应返回统一的"用户名或密码错误"，不泄露具体错误项。
3. 当同一账号连续失败登录达到 5 次时，系统应锁定该账号 15 分钟。**锁定期间系统不校验凭据、不累计失败计数、不返回凭据类错误，仅返回 HTTP 423 + 锁定状态与剩余分钟数；锁定期满自动解锁且失败计数清零，其后失败从 0 重新累计。**
4. 当登录成功时，系统应将失败计数器重置为零。
5. 系统应以 BCrypt（cost ≥ 12）存储密码；任何接口与日志不得出现明文密码。后台密码复杂度：≥ 10 位且同时包含大写字母、小写字母、数字与特殊字符（适用于创建、重置、修改个人密码）。
6. 当登录成功或失败发生时，系统应记录审计日志（账号、IP、User-Agent、结果、时间）。**未认证尝试（失败登录、验证码错误）`operator_id` 为空，`operator_name` = 请求提交的用户名（原样截断至 30 字）；成功登录 `operator_id` = 账号主键。**
7. 验证码应一次有效，校验后立即作废，有效期 2 分钟（默认值见附录 A）。
8. 当会话不活动超过 30 分钟时，系统应使其过期；会话应支持滑动续期。
9. 同一账号的并发会话数上限可经系统配置调整（默认 5，附录 A）；超出时按"最早登录会话先失效"策略踢出，被踢会话收到明确的 401 语义。
10. 系统应提供修改个人密码接口：验证旧密码，新密码满足复杂度要求；成功后当前会话保留、该账号其他会话立即失效，并记录审计。
11. 登录与验证码接口按"IP + 账号"双维度限流（默认阈值见附录 A）。
12. 登录请求可携带可选设备标识，用于在线会话展示（R6）。
13. **令牌载体契约：** 后台会话令牌经 `Set-Cookie` 下发（HttpOnly + Secure + SameSite=Strict）。后台写操作 CSRF = 双重提交：登录同时经非 HttpOnly CSRF Cookie（SameSite=Strict）与响应体 `csrfToken` 下发**同一值**（Cookie 为权威载体，data 供前端读取便利）；客户端把该值放到请求头 `X-CSRF-Token`，服务端常量时间比较，缺失/不一致 → 403。门户会话令牌经响应体下发、请求以 `Authorization: Bearer <token>` 携带（门户不做 CSRF）。两侧令牌均为服务端会话态（非自包含 JWT），令牌字符串携带账号类型前缀（`admin:` / `client:`），格式上不可互换。**401 原因码：** 后台统一 `auth.session.invalid`；门户封闭四码见 R4.3。

#### 正确性属性

1. **锁定触发不变量：** 若 failed_attempts ≥ 5，则 locked_until = 当前时间 + 15 分钟。
   - **类型：** 后置条件　**测试策略：** 随机失败/成功登录序列，恰在第 5 次连续失败锁定、成功即清零。
2. **审计完整性：** 每次登录尝试（成功或失败）恰好产生一条审计记录。
   - **类型：** 不变量　**测试策略：** 并发登录序列，审计条数与尝试次数一一对应（基于审计经 Outbox 可靠投递，见 R10.3）。
3. **改密会话失效正确性：** 修改密码后，签发于修改前的其他会话全部失效，当前会话有效。
   - **类型：** 后置条件　**测试策略：** 多会话登录 → 改密 → 逐个校验。

### 需求 2：基于角色的权限控制（RBAC）

**用户故事：** 作为系统管理员，我希望通过角色为后台账号分配菜单与操作权限，以便不同岗位只能看到并操作其职责内的功能。

#### 验收标准

1. 权限模型包含：后台用户 — 角色 — 权限；一个用户可绑定多个角色，最终权限为并集。**角色属性：编码（全局唯一，3–30 位 `[a-z0-9_-]`）、名称、描述、状态（启用/停用）、是否内置、创建/更新时间；停用角色的权限不计入用户权限并集，用户与角色的绑定关系保留。**
2. 权限分两类统一树形管理：菜单权限（导航与页面路由）与操作权限（按钮 / API，编码格式 `域:资源:操作`）。**权限树的节点即菜单；每个操作权限必须归属唯一菜单节点（API 鉴权只看权限码，与菜单无运行时依赖，挂载仅用于树形管理）。** 全量权限码约定见**附录 B 权限码矩阵**，新功能交付必须同步登记。
3. 当用户访问未授权的后台 API 时，系统应返回 403 并记录审计日志。
4. 系统应提供"当前用户菜单树"接口：**仅返回用户有权访问的菜单及其子树**，管理后台据此动态渲染导航与路由。
5. 系统应内置超级管理员角色（拥有全部权限，不可删除、不可修改其权限集）。

### 模块 C：任务引擎

### 需求 11：任务定义与编排

**用户故事：** 作为运营人员，我希望以聚合方式配置任务——基本信息、周期、参与控制（互斥/灰度/过滤）、步骤流（五类步骤与条件分支）、平台动作——以便一次保存完整任务。

#### 验收标准

1. 任务基本属性：任务编码（全局唯一）、名称、描述、生效时间窗、列表排序权重、任务分类（如 日常任务/新人任务/限时活动，分类来自字典）、展示装饰（图标 URL、角标文案如"热门/新人"）。
2. 步骤五类：引导（展示即自动完成）、点击、回调、进度（累计达标）、发奖；步骤编码任务内唯一，带顺序号与进度目标值（PROGRESS 用）、奖品引用（REWARD 用）；**单任务步骤数上限默认 50（附录 A），首步骤允许为 REWARD（纯发奖任务，领取即发奖完成）；PROGRESS 的目标值与单次上报 value 均为正整数（1–2^31−1），单次 value 上限 1000，超出按参数非法拒绝**。
3. 条件分支：转移边（来源→目标）+ 条件表达式 + 优先级；全部转移边构成有向无环图，禁止回跳与环。一步完成后按优先级升序求值，第一条命中边生效。**空表达式 = 无条件边（恒命中）**；全部边都不命中时按"当前步骤顺序号 + 1"兜底（无该步骤则实例完成）。步骤顺序号任务内唯一、从 1 起的正整数，允许空洞。
4. 草稿态聚合保存：任务主体 + 步骤 + 分支 + 参与控制 + 平台动作一次保存，全部成功或全部回滚。
5. 表达式校验接口：保存前可验证条件表达式与过滤表达式的合法性（语法 + 函数白名单 + **空值语义模拟求值**：对属性缺失的样例用户报告将判 false 的条件）。
6. 互斥组独立管理（编码、名称、是否跨周期互斥），任务可关联至多一个互斥组。**互斥判定语义：非跨周期 = 同组内存在与本次领取相同 cycleKey 的未完成（IN_PROGRESS）实例时阻止；跨周期 = 同组内存在任意 cycleKey 的未完成实例即阻止，直至实例转终态。校验约束：同互斥组内全部任务必须为同一周期类型，否则任务保存拒绝。**
7. 任务周期五种：一次性、每日、每月、CRON、自定义时段。**cycleKey 生成规则（时区 UTC+8）：一次性 = 固定值 `NONE`；每日 = `yyyyMMdd`；每月 = `yyyyMM`；CRON = 周期起点时刻格式化 `yyyyMMddHHmmss`（CRON 采用标准 5 段表达式"分 时 日 月 周"，最小粒度分钟，任意两次触发间隔 ≥ 1 小时，保存时校验）；自定义时段 = 运营配置的时段标识，格式为起止拼接 `yyyyMMddHHmmss-yyyyMMddHHmmss`。cycleKey 字段长度 ≤ 40 字符。**
8. 灰度四种：不灰度、百分比、AB 分组、人群包定向（灰度配置里的允许/排除包，**与第 9 条过滤人群包独立，判定 AND**）。**分桶算法（与术语表同一函数）：`v = md5(userId + ":" + taskId)` 摘要前 8 字节按大端组成无符号 64 位整数，`bucket = remainderUnsigned(v, 100)`（输出 [0,100)）。百分比：当且仅当 `bucket < percent` 可见（percent=0 恒不可见、100 恒可见）；AB 分组：`bucket` 为偶数入 A 组、奇数入 B 组，grayConfig 指定命中的可见分组（A / B / AB 均可见）。标准测试向量：(userId,taskId)→bucket 为 (1,1)→81；(1,2)→0；(10001,88)→32。**
9. 任务过滤 = 表达式过滤 + 人群包定向（允许人群包 / 排除人群包）叠加。**表达式 DSL（封闭规范）：字面量 = 单引号字符串与整数；比较运算符 `= != > >= < <= in not-in`；逻辑运算符 `AND OR NOT`（优先级 NOT > AND > OR）+ 括号分组；函数全量白名单（新增须修订本条）：`province()` 返回省份码、`userLevel()` 返回等级整数、`hasTag(string)` 标签集合包含判定、`userRole()` 返回角色码、`orgId()` 返回组织 ID、`registerWithinDays(int)` 注册至当前 ≤ N 天判定、`inCrowd(string)` 人群包包含判定；**属性缺失时含该属性的条件求值为 false（默认不可见）。**过滤人群包判定顺序：配置了允许包则必须命中至少一个，再命中任一排除包即不可见；包不存在或停用按不可见处理并告警。**
10. 平台动作两层：任务级与步骤级，按端（Web/Android/iOS/小程序/模拟端）配置动作类型与参数。**动作类型与参数 schema（封闭）：无动作 `{}`；站内跳转 `{ "route": <预注册路由名，≤64 位，在字典 portal_route 中登记维护>, "params"?: object }`；外链 `{ "url": <https URL，≤512 字符> }`；原生路由 `{ "scheme": <≤128 位字符串> }`；公共可选参数 `buttonText`（≤16 字符）。**
11. 任务复制：复制主体与全部子配置，编码与名称自定义。
12. 任务删除仅逻辑删除；已发布任务不可删除。
13. 人群包管理：命名、编码唯一（4–64 位 `[a-z0-9_-]`）、导入用户 ID 列表（**纯文本每行一个用户 ID；单包上限 100,000 条，附录 A `crowd.max-size`；重复行自动去重；不存在的用户 ID 跳过；导入结果报告含 成功/去重/无效 三类计数**）、条目数统计、启用/停用。任务编码同规则（4–64 位 `[a-z0-9_-]`，全局唯一）。

#### 正确性属性

1. **聚合保存原子性：** 聚合保存要么全部子配置持久化成功，要么数据库无任何变化。
   - **类型：** 不变量　**测试策略：** 注入子配置写入失败，断言任务主体同样未落库。
2. **流程图无环不变量：** 合法保存的转移边集合无环且目标顺序号恒大于来源顺序号。
   - **类型：** 不变量　**测试策略：** 随机生成步骤与转移边，校验器接受集恰为无环前向集合。

### 需求 12：任务发布与版本快照

**用户故事：** 作为运营人员，我希望发布任务并让每个版本的行为固化，以便已领取用户不受后续修改影响。

#### 验收标准

1. 任务主状态机合法流转全表：`DRAFT→SCHEDULED`（设定时）、`DRAFT→PUBLISHED`（立即发布）、`SCHEDULED→DRAFT`（取消定时）、`SCHEDULED→PUBLISHED`（到点发布或手动提前发布）、`PUBLISHED→OFFLINE`（下线）、`OFFLINE→DRAFT`（重新编辑）；其余状态组合一律拒绝。版本号从 0 起（未发布草稿）；**真正落快照的发布**（DRAFT/SCHEDULED→PUBLISHED，以及 PUBLISHED 修订发布）成功则 +1。SCHEDULED 修订按 R12.2 不 +1。
2. **编辑模型：** 对已发布/已定时任务的编辑产生"修订草稿"（编辑副本），主状态保持不变、线上行为不变。**PUBLISHED 任务发布修订草稿 = 版本号 +1 并生成新快照，仅对新实例生效（存量实例仍按旧快照）。SCHEDULED 任务发布修订草稿 = 仅替换待定时发布的内容并清除修订标记，不增加版本号、不生成快照，主状态保持 SCHEDULED；到点仍按 R12.5 重新校验后 +1 并固化。**
3. 发布完整性校验：至少一个步骤；REWARD 步骤必须配置启用状态的奖品；全部表达式合法；时间窗有效（开始 < 结束）；**步骤可达性静态校验：终点步骤 = 无出边的步骤；要求从首步骤沿转移边可达每个步骤，且每个非终点步骤至少有一条出边（不存在死锁步骤）；不要求终点为 REWARD，任一路径抵达终点即实例完成；定时发布时间必须早于时间窗结束时刻**。
4. 发布成功将全量配置固化为不可变版本快照（版本号自增），任务对目标用户可见。
5. 定时发布与取消定时；到点自动发布（到点时重新执行全部校验）。**校验失败：主状态保持 SCHEDULED（不是 DRAFT），待发布内容保留，不 +version、不落快照**；并经可观测性告警通道（webhook，环境变量配置）通知 + 后台"定时发布失败记录"列表展示，两种途径均为交付物。
6. 下线立即使任务不可见不可领取；存量实例按其绑定快照继续执行直至完成、放弃或过期（R14.10）。
7. 重新发布（发布修订草稿）前系统应向操作者提示"新实例将使用新版本，存量实例不受影响"，需二次确认。
8. 版本历史查询与任意两版本结构化差异对比（按步骤/分支/过滤/平台动作分组）。
9. 批量发布/下线：单批 ≤ 50，逐条成败明细，单条失败不影响其他；单任务内部（状态+快照）原子。
10. 发布、下线记录审计（操作人、时间、版本号）。

#### 正确性属性

1. **快照不可变性：** 实例绑定的快照内容在其整个生命周期内不被任何后续操作改变。
   - **类型：** 不变量　**测试策略：** 领取实例 → 修改并重新发布 → 断言实例按旧快照渲染与推进。
2. **修订草稿隔离性：** 修订草稿的存在与编辑不影响线上实例的任何行为。
   - **类型：** 不变量　**测试策略：** 编辑副本保存/放弃过程中并发执行 C 端流程，行为不变。
3. **批量任务级原子性：** 批量操作中每个任务独立成败，单个任务内部变更原子。
   - **类型：** 不变量　**测试策略：** 混合合法/非法任务批量发布，合法者全部生效、非法者无变化。

### 需求 13：任务可见性与领取（C 端）

**用户故事：** 作为 C 端用户，我希望看到向我投放的任务并领取参与，以便完成任务获得奖励。

#### 验收标准

1. 投放列表仅返回同时满足：主状态 PUBLISHED、时间窗内、灰度命中、过滤通过（表达式 + 过滤人群包）的任务；支持按分类筛选、按排序权重输出、分页。**例外：用户已有该任务当前 cycleKey 的 `IN_PROGRESS` 实例时，即使此刻不再命中灰度/过滤，仍出现在列表并标进行中。** OFFLINE / 未发布任务不出现在投放列表。**用户命中用户维度黑名单时投放列表返回空（进行中入口改走「我的任务」R13.3）。**
2. 列表对每个任务展示用户状态：未开始（领取入口）/ 进行中（继续入口）/ 终态（已完成、已放弃、已过期——仅展示不可操作），进行中任务入口直达当前步骤。
3. "我的任务"视图：当前用户全部非进行中实例（已完成/已放弃/已过期）与进行中实例的分页列表（含进度概要与分类筛选）。
4. 任务卡片曝光由客户端按 R28.13 / 附录 D `task.card.exposure` 上报，列表接口不写服务端事件，不阻塞列表响应。
5. 任务详情：有 `IN_PROGRESS` 实例则**始终按快照渲染步骤并可推进**（即使任务已 OFFLINE 或已离开时间窗，直到完成/放弃/过期）。无实例时：任务 OFFLINE / 不可见 → 200 + 状态「已结束」（R34.6），不暴露风控原因。
6. 领取前校验链依次为：账号状态 → **实例幂等短路（R13.7：已有实例不论终态一律 200 返回，其后各步不再执行）** → 可见性（与投放列表同源）→ 风控（R25 + R26）→ 互斥组 → 每日领取上限（每用户每日成功**新建**实例数，跨任务全局，默认见附录 A）。任一不过即拒绝并返回可理解提示。
7. 同一用户 + 同一任务 + 同一 cycleKey 仅一个实例。`start` 遇已有实例：**不论是否终态，一律 200 幂等返回该实例**（不新建、不计每日上限）。一次性任务（cycleKey=`NONE`）放弃/过期/完成后再次 start 仍返回该终态实例，等价于不可再领。
8. 领取成功（新建）即创建 `IN_PROGRESS` 实例并 `enter` 首步骤（PASSIVE 自动完成并级联）。
9. C 端支持放弃 `IN_PROGRESS` 任务（转 `ABANDONED` 并释放互斥占用）；周期任务下一 cycleKey 可再领。**实例记录 `abandonSource`（USER / ADMIN，R14.8）与放弃时间；C 端文案统一「已放弃」，后台可按来源筛选。**

#### 正确性属性

1. **实例唯一性不变量：** 并发 N 次同（用户，任务，cycleKey）领取，最终恰 1 个实例，全部请求成功返回该实例或幂等返回。
   - **类型：** 不变量　**测试策略：** 并发集成测试，断言唯一约束与幂等响应。
2. **灰度稳定性：** 灰度配置不变期间，同一用户对同一任务版本的可见性判定恒定。
   - **类型：** 不变量　**测试策略：** 随机用户集重复判定，结果恒定。
3. **埋点非阻塞：** 列表接口响应时间与埋点写入耗时无关。
   - **类型：** 不变量　**测试策略：** 注入埋点存储故障，列表接口正常返回。
4. **风控拒绝幂等：** 被风控拒绝的领取请求不产生任何实例或状态变化，重复请求结果一致。
   - **类型：** 不变量　**测试策略：** 黑名单用户重复领取，无实例、响应一致、每次各记录一条命中。

### 需求 14：步骤推进引擎

**用户故事：** 作为 C 端用户与外部系统，我希望任务步骤被可靠推进（点击/回调/进度）并按条件分支走通全流程。

#### 验收标准

1. 引擎四入口：进入实例（enter）、点击（click）、回调（callback）、进度上报（progress）。
2. 引导步骤被激活时自动完成并级联，直至遇到需用户或外部动作的步骤。
3. 点击步骤由 C 端点击接口完成；回调步骤仅由 internal 回调完成；进度步骤按上报累加，达到目标完成。**进度去重按（实例、步骤、reportId）数据库唯一约束实现，去重判定与进度累加在同一事务；累加遇乐观锁冲突自动重试 ≤ 3 次，重试耗尽返回"处理中"业务码（外部系统按 at-least-once 重投，由 reportId 去重兜底不重复累加）**。
4. 每步完成后按 R11 分支规则确定下一激活步骤；无后续步骤时实例转完成。
5. REWARD 步骤完成条件 = 发放记录创建成功（领取状态进入 `WON` 或 `GRANTED`，见 R18.1）。履约是否到账不阻塞步骤推进。发放结果分两类处理，**失败分类为封闭枚举，由发放处理器显式声明，不允许运行时猜测**：
   - **可重试失败**：系统异常（如存储超时）、库存不足（等待回补/释放）——步骤不完成、实例不推进，经自动重试（R18.5）或后台人工重试（R18.6）。
   - **永久失败**（业务性不可重试，封闭枚举）：`PRIZE_DISABLED`（奖品停用）、`PRIZE_DELETED`（奖品删除）、`USER_INVALID`（用户停用/删除）——发放记录转永久失败，步骤标记"发放失败"并跳过（SKIPPED），实例继续推进；后台补发入口（R17.5）作为补偿路径，用户侧展示"奖励发放失败"提示。
6. 步骤完成幂等：重复点击/回调不得二次推进或二次发奖；重复进度上报按 reportId 去重丢弃（不累加）；**进度/回调上报到达非当前（未激活或已完成）步骤时按"步骤状态不符"拒绝**。
7. 同一实例并发推进请求收敛为恰一次生效（乐观锁 + 唯一约束兜底）。
8. 实例支持运营侧终止（ABANDONED，`abandonSource=ADMIN`，权限 `task:instance:abandon`）与用户侧放弃（`abandonSource=USER`，R13.9），均释放互斥占用。
9. **后台实例管理：** 按任务/用户/状态/时间的实例分页查询；实例详情含步骤状态明细、事件时间线（来自事件查询）；终止入口与权限控制。
10. **实例过期：** `base = min(快照时间窗结束, 任务下线时刻, 当前周期结束)`（缺省项视为 +∞；周期结束 = 下一 cycleKey 起点 − 1ms）。若 `base` 仍为 +∞（无窗且未下线的一次性任务），则 `base = 领取时刻`。`expireAt = base + N 天`（默认 7，附录 A）。下线后重新发布：按最近一次下线时刻与当前时间窗重新取 min。超过 expireAt 仍未完成的实例由定时任务转 EXPIRED 并释放互斥；到期不可再推进。
11. 步骤与实例状态全量落服务端事件（经 R28 Outbox，编码见附录 D）：新建实例 → `task.instance.start`；步骤获得完成权 → `task.step.complete`；实例 `COMPLETED` → `task.instance.complete`；放弃/运营终止 → `task.instance.abandon`；过期翻转 → `task.instance.expire`。实例记录开始到完成耗时（秒），供查询与看板；R26 R-e 不读该字段，改用调用方传入的 `elapsedSeconds`（见 R26.1）。

#### 正确性属性

1. **推进恰一次：** 任意并发/重复推进序列后，每个步骤至多完成一次、每个 REWARD 步骤至多触发一次发放。
   - **类型：** 不变量　**测试策略：** 同实例并发 click/callback/progress，步骤完成记录唯一、发奖记录唯一。
2. **进度去重正确性：** 同一 reportId 的重复上报只产生一次进度累加。
   - **类型：** 不变量　**测试策略：** 并发/重复上报同 reportId，进度增量恰一份。
3. **状态机合法性：** 步骤流转仅允许 `未激活 → 可执行 → 已完成/跳过（含发放失败跳过）`，已完成状态不可回退。
   - **类型：** 不变量　**测试策略：** 随机合法操作序列，任意时刻状态合法。
4. **过期终局性：** 实例转为 EXPIRED 后任何推进请求被拒绝且状态不再改变。
   - **类型：** 不变量　**测试策略：** 时间推进至过期后发起各入口推进，全部拒绝。

### 需求 15：外部回调与进度上报（internal API）

**用户故事：** 作为外部业务系统，我希望通过签名鉴权的内部接口回调步骤与上报进度，以便驱动 CALLBACK/PROGRESS 步骤完成。

#### 验收标准

1. 内部端点：步骤回调与进度上报，均支持按实例 ID 或（用户 ID + 任务编码 + cycleKey）定位，并**必须携带 stepCode 定位到具体步骤**。请求体契约：CALLBACK = `{ instanceId | (userId + taskCode + cycleKey), stepCode, bizNo? }`（bizNo 为外部业务号，仅记录用于对账）；PROGRESS = `{ instanceId | (userId + taskCode + cycleKey), stepCode, value, reportId }`。**进度上报必须携带 reportId（调用方业务流水号），系统按（实例、步骤、reportId）数据库唯一约束去重（与累加同事务，崩溃安全）**。
2. 调用方登记制：每个外部调用方分配 appId + secret（后台登记、支持密钥轮换与失效）。**签名规范：`stringToSign = METHOD(大写) + "\n" + PATH(含 query string) + "\n" + TIMESTAMP + "\n" + NONCE + "\n" + HEX(SHA-256(body 原始字节))`（空 body 按 SHA-256(空串)）；签名 = HMAC-SHA256(secret, stringToSign)，输出小写十六进制置于请求头 `X-Sign`；随头携带 `X-App-Id`、`X-Timestamp`、`X-Nonce`。** 时间戳容差 ±5 分钟，nonce 去重窗口 10 分钟（附录 A），常量时间比较。
3. 重复投递幂等（回调幂等见 R14.6；进度按 reportId 去重）。
4. 失败返回结构化可区分错误：签名无效、调用方不存在/失效、实例不存在、步骤状态不符、参数非法、**处理中（进度累加冲突重试耗尽，可按 reportId 原样重投，不重复累加）**。
5. `/internal/**` 不暴露于公网路由，应用层签名校验兜底；internal 调用按 appId 维度限流（附录 A）。

#### 正确性属性

1. **防重放不变量：** 时间戳超容差或 nonce 在去重窗口内重复的请求必须被拒绝，且拒绝不改变业务状态。
   - **类型：** 不变量　**测试策略：** 重放/篡改/过期样本全部拒绝。

**用户故事：** 作为运营人员，我希望同一步骤在不同客户端展现不同交互，各端体验最优且配置一处维护。

   - **类型：** 不变量　**测试策略：** 集成测试：发布 → 改定义 → 断言进行中实例 action 不变。
4. **端标识白名单：** 端标识由服务端按请求头解析并白名单校验（合法值：WEB/ANDROID/IOS/MINIAPP/SIMULATOR），非法或缺失按 WEB 处理。
   - **类型：** 后置条件　**测试策略：** 单元测试覆盖五端原样解析与非法/缺失回退。

### 需求 17：奖品配置与库存

**用户故事：** 作为运营人员，我希望配置奖品及其库存与限制规则，以便控制成本与投放节奏。

#### 验收标准

1. 奖品必须归属一个**已启用的奖品分类**（R17.8）。奖品属性：编码唯一（4–64 位 `[a-z0-9_-]`）、名称、展示图片（外链 URL）、展示描述、分类编码、类型参数（按分类参数契约：积分类必填正整数面额 `points`；面额成本类必填正整数 `faceFen`；第三方分类可覆盖 `adapterCode`，缺省用分类默认适配器）、**单价成本 `unitCostFen`（分，仅分类成本算法 = 固定单价时必填且 >0）**、总库存（正整数）、**领取限制：每日限领 `dailyClaimLimit`（正整数，0=不限）、累计限领 `totalClaimLimit`（正整数，0=不限）、地域限制 `regionLimit`（省份码数组，空=不限，命中任一即通过）、等级限制 `levelLimit`（等级码数组，空=不限，命中任一即通过）、标签限制 `tagLimit`（标签码数组，空=不限，拥有任一即通过）**、领取方式（自动发放/手动领取）、有效期策略（发放后 N 小时过期，空=永不过期；**积分类奖品的有效期即积分入账时 expireAt 的唯一来源，与 R20.4 为同一配置，禁止独立维护**）、奖品组、状态（草稿/启用/停用）、扩展配置。**奖励目标与履约方式取自分类，草稿保存时写入奖品快照；启用后不可改分类、目标、履约方式与成本算法相关字段。** 积分类强制 `PLATFORM` + `INSTANT`；第三方分类强制 `ASYNC`。**奖品状态流转：草稿→启用、启用→停用、停用→启用（需重新执行第 7 条影响确认）；其余拒绝。删除仅草稿态可逻辑删除；被任何在线版本快照引用的奖品禁止删除。**
2. 库存扣减为数据库原子操作，绝不超发；不足时发放失败并落失败记录。
3. 发放前置校验为有序规则链：奖品状态 → 库存 → 用户当日限领 → 用户累计限领 → 地域 → 用户等级 → 用户标签 → 风控校验（R25/R26）；任一不过即拒绝并返回命中规则。
4. 库存变更留痕：每笔扣减/回补记录前后值、关联业务、时间。**回补走管理端库存回补（权限 `reward:prize:stock-replenish`，正整数、必填原因、`REPLENISH` 留痕），作为 R17.5 补发库存不足的前置。**
5. 管理员手动补发（权限 `reward:record:manual-grant` + 审计）：**必须扣减库存（库存不足时需先经库存回补流程并留痕）**；可绕过的规则仅限地域/等级/标签三项运营规则；奖品状态、限领、风控规则不可绕过；补发记录独立留痕并计入审计必记清单。
6. 奖品组独立维护并用于业务圈选。
7. 停用被在线版本快照引用的奖品时，系统应要求二次确认并展示受影响任务数与**在途实例数（口径：当前状态为进行中、且其绑定版本快照中存在引用该奖品的未完成 REWARD 步骤的实例数，实时查询）**；停用后新发放被拒（永久失败 `PRIZE_DISABLED`，R14.5 路径），存量已发放记录不受影响。
8. **奖品分类目录（可扩展）：** 分类独立维护（权限 `reward:category:*`）：编码、名称、奖励目标、履约方式、成本算法、是否渠道对账、**对账动作政策 `reconActionPolicy`（`REVIEW` / `AUTO`，仅 `reconRequired=true` 生效；须对账内置三类默认 `REVIEW`；启用后仍可改）**、默认适配器、参数契约、内置标记、启停。**内置分类不可删除**：`POINTS`（积分）、`ALIPAY_RED`（支付宝红包）、`WECHAT_RED`（微信红包）、`PHONE_CREDIT`（话费）、`COUPON`（优惠券）、`BADGE`（徽章）、`PHYSICAL`（实物）。新增分类 = 登记一行（第三方另实现同名适配器）；不改表枚举。停用分类后不可新建该分类奖品，存量奖品仍按自身快照履约。奖品可覆盖 `reconActionPolicy`（空 = 继承分类，启用后仍可改，不冻结）。门禁语义见 R37.7。
9. **成本算法（分类级，金额单位人民币分）：** `NONE`（无现金成本，如积分/徽章，记录 `costFen=0`）；`FIXED_UNIT`（奖品 `unitCostFen`，实物等）；`FACE_VALUE`（`typeParams.faceFen`，红包/话费等面额即成本）。**发放记录写入时快照 `categoryCode`、`faceFen`、`costFen`**；之后改奖品单价或分类默认值不影响已有记录。花销统计只计 `simulated=0` 且履约 `ARRIVED` 的 `costFen` 之和；`SENDING` 为在途成本，失败/过期不计花销。

#### 正确性属性

1. **不超发不变量：** 任意并发发放序列后，`成功发放数 + 剩余库存 = 总库存` 恒成立（含补发与冲正路径）。
   - **类型：** 不变量　**测试策略：** N 线程争抢库存 S，成功数 = S 且余量 0；补发/冲正后等式仍成立。
2. **限领原子性：** 用户当日/累计限领在并发下不被突破。
   - **类型：** 不变量　**测试策略：** 并发领取，超限请求全部被拒。
3. **成本快照不可变：** 记录落地后改奖品 `unitCostFen` 或分类成本算法，该记录的 `costFen` / `faceFen` 不变。
   - **类型：** 不变量　**测试策略：** 发放成功后改单价再查记录与花销汇总，历史行金额不变。

### 需求 18：奖励发放

**用户故事：** 作为 C 端用户，我希望完成任务后奖励被准确发放，不多发不漏发。

#### 验收标准

1. **发放记录只表示领取状态，不持有资产。** 发放动作完成 = 记录创建成功（自动发放进入 `GRANTED`，手动领取进入 `WON`）。REWARD 步骤以此为完成条件，不等待履约到账。
2. **领取方式决定记录何时进入 `GRANTED`：** 自动发放 = 发放事务内写入 `GRANTED`；手动领取 = 发放事务只落到 `WON`，用户 `claim`（R19）成功后再转 `GRANTED`。积分类允许配置为手动领取，语义同上。
3. **履约（到账）独立于领取状态，封闭四态 `NONE | SENDING | ARRIVED | FULFILL_FAILED`：**
   - `INSTANT` + `PLATFORM`：记录进入 `GRANTED` 的同一事务内完成本平台入账（POINTS 走积分 `earn`；其余本平台类型无独立账本，记 `ARRIVED`）。用户见「已到账」。
   - `ASYNC`：记录进入 `GRANTED` 后履约为 `SENDING`（发送中）。`PLATFORM` 由后台确认到账（权限 `reward:record:fulfill`）。`THIRD_PARTY`：**P0 适配器为桩**——发放事务内不调第三方，桩受理后写 `SENDING`；到账**只**经 `/internal/reward/fulfillment/callback` 或后台 `fulfill-confirm`（`reward:record:fulfill`）转到 `ARRIVED` / `FULFILL_FAILED`。真实渠道 SDK/轮询属分类启用后的增量，不阻塞 P0。
   - 同一发放记录至多一次 `ARRIVED`。发送失败可按附录 A 自动重试；超限或发送超过 `reward.fulfill.sending-timeout-hours` 转 `FULFILL_FAILED`。**履约失败原因封闭枚举**（写入 `fulfillFailReason`）：`TIMEOUT`（发送超时）/ `ADAPTER_ERROR`（适配器/系统异常）/ `CHANNEL_REJECT`（渠道明确拒绝）/ `CALLBACK_FAILED`（回执失败）/ `MANUAL`（后台标记失败）。超时路径必须写 `TIMEOUT`。后台履约重试不重走库存与领取状态机。进入 `GRANTED` 时按 R17.9 写入成本快照；须对账分类在 `ARRIVED` / 跨对账日仍 `SENDING` / 转入 `FULFILL_FAILED` 后进入待对账（R37.2）。
4. 发放幂等：同一（业务来源， 来源 ID， 奖品）至多一条成功发放记录。**业务来源封闭枚举 `grantSource ∈ { TASK_STEP, SIGNIN_DAY, ACTIVITY_PARTICIPATION, MANUAL_GRANT, SIMULATE }`；来源 ID 依次 = 实例步骤执行记录 ID / 签到记录 ID / 活动参与记录 ID / 补发申请单 ID / 模拟操作单 ID。**
5. **领取状态机（七态，全量流转）：**
   - 自动发放型：`PENDING → GRANTED`；`PENDING → RETRY_PENDING →(重试) GRANTED / PERMANENT_FAILED`。
   - 手动领取型：`PENDING → WON（待领取）→ CLAIMING（领取中）→ GRANTED`；`CLAIMING → RETRY_PENDING`；`RETRY_PENDING →（用户手动重试 CAS）CLAIMING`（与自动重试共享 `reward.claim.retry-max`，R19.4）；`CLAIMING / RETRY_PENDING → GRANTED / PERMANENT_FAILED`；`WON → EXPIRED`（过期翻转）；`RETRY_PENDING → EXPIRED`（与 WON 同批扫描）。
   - 后台人工重试：`PERMANENT_FAILED → GRANTED`（`reward:record:retry` 成功，重走规则链与库存扣减，retry_count 归零）。
   - 永久失败封闭枚举见 R14.5。
   - 失败重试为异步调度任务：进入 RETRY_PENDING 后步骤保持 ACTIVE，由调度按可配置间隔重试（默认 3 次，间隔见附录 A）；自动/人工/推进重触发的并发由发放幂等（R18.4）兜底。
6. 后台发放记录查询（用户/奖品/领取状态/履约状态/时间）、领取失败重试（`reward:record:retry`）与履约确认/重试（`reward:record:fulfill`），均审计。
7. **风控拒绝的发放：不产生发放记录与任何副作用（含库存不变），仅落风控命中记录（R27），后台在命中记录中可见"风控拦截"原因与可跳转用户。**

#### 正确性属性

1. **发放恰一次：** 任意重试与并发序列后，同一业务来源对同一奖品至多一条领取状态为 `GRANTED` 或 `WON`/`CLAIMING`/`RETRY_PENDING` 的有效记录；履约 `ARRIVED` 至多一次。
   - **类型：** 不变量　**测试策略：** 并发+重试集成测试，唯一约束与终态唯一；异步履约回调重放不二次到账。
2. **风控拦截零副作用：** 被风控拒绝的发放路径上，发放记录表、库存、积分账户均无变化。
   - **类型：** 不变量　**测试策略：** 黑名单/规则命中用户的发奖链路，断言三表无变化、命中记录存在。

### 需求 37：奖品成本与渠道对账

**用户故事：** 作为运营与财务，我希望按分类看到真实花销，并把红包/话费等渠道账单与平台记录核对；对不上时能补发或认领差异。

#### 验收标准

1. **花销查询（P0，不依赖看板 R23）：** 按分类、奖品、时间窗汇总：到账笔数、到账成本（分）、在途笔数、在途成本；模拟数据不计。明细可下钻到发放记录（含 `costFen`、`faceFen`、`fulfillmentRef`）。
2. **须对账分类**（分类 `reconRequired=true`，内置：支付宝红包、微信红包、话费）：履约进入 `ARRIVED`、停留 `SENDING` 超过对账日、或转入 `FULFILL_FAILED` 的记录进入待对账。积分类、徽章等不对账。
3. **对账批次：** 后台按（分类 + 账单日）创建批次（权限 `reward:recon:query/import/match/action` + 审计）。导入渠道账单行：`fulfillmentRef`、`amountFen`、渠道时间。P0 为文件/JSON 导入；渠道官方拉单属适配器能力，有则调用，无则只走导入。
4. **核对键 = `fulfillmentRef`（`{adapterCode}:{externalId}`）。** 结果封闭：`MATCHED`（双方有且金额相等）、`PLATFORM_ONLY`（平台有渠道无）、`CHANNEL_ONLY`（渠道有平台无）、`AMOUNT_MISMATCH`（双方有金额不等）。同一批次内每条平台待对账记录、每条渠道行至多出现一次。
5. **差异处置（每条差异一次有效动作，审计；须先过 R37.7 门禁）：**
   - `PLATFORM_ONLY` 且履约为 `SENDING` / `FULFILL_FAILED`：履约重试（`REFULFILL`，不新建记录、不扣第二次库存）或补发（`MANUAL_GRANT`，扣库存，`sourceId` 关联对账差异 ID，R17.5 规则全适用）。**补发成功与新发放同事务：原单履约置 `FULFILL_FAILED` 且 `fulfillFailReason=MANUAL`（已是该态则只回写原因）；原 `fulfillmentRef` 此后任何到账回调 / 后台 confirm 必须拒绝改态（HTTP 200 幂等，履约保持失败）。不调用渠道撤销。**
   - `PLATFORM_ONLY` 且履约已 `ARRIVED`：禁止履约重试与补发（平台已记到账，渠道缺失属账务差异）；只允许认领（`ABSORB`）。
   - `CHANNEL_ONLY`：补记发放记录（`LEDGER_ONLY`，不重复履约，标记来源对账认领）或认领为费用差异（`ABSORB`，只记账不给用户）；一律人工。
   - `AMOUNT_MISMATCH`：只允许备注认领（`ABSORB`），不自动改 `costFen`（历史快照不可改）；花销报表以平台快照为准，差异金额单独列。
6. 对账不改领取状态机；补发仍走统一发放（库存、限领、风控）。渠道账单金额与平台 `costFen` 不一致不得悄悄改快照。
7. **补发 / 履约重试门禁（分类 + 奖品可配，原因强制）：**
   - **有效政策** = 奖品 `reconActionPolicy`（空则继承分类）∈ {`REVIEW`, `AUTO`}。须对账内置三类分类默认 `REVIEW`。政策可随时改，不影响已确认的差异项。
   - **补发（`MANUAL_GRANT`，新开一笔发放）永不自动**，必须人工点选。
   - **须先人工核渠**（差异项 `reviewStatus` 到 `CONFIRMED` 之前，`REFULFILL` / `MANUAL_GRANT` 一律拒绝），不论政策：履约失败原因 = `TIMEOUT`；履约仍为 `SENDING`（在途，渠道可能已出款）；失败原因缺失或非封闭值。核渠入口：`PENDING_REVIEW` → 操作人确认「已核渠，渠道未出款」（`CONFIRMED`，必填备注）或「渠道已出款 / 无需处理」（`REJECTED`）。`REJECTED` 后只允许 `ABSORB`。
   - `CHANNEL_REJECT` / `ADAPTER_ERROR` 的 `FULFILL_FAILED`：`REVIEW` 时人工可直接动作（渠道已明确未出款）；`AUTO` 且附录 A `reward.recon.auto-refulfill-enabled=true` 时，匹配完成后系统只自动跑 **`REFULFILL`**（同一笔）。P0 该开关默认 `false`（适配器为桩，避免空转）。
   - 匹配完成后：须核渠的项置 `PENDING_REVIEW`；其余 `reviewStatus=NONE`。

#### 正确性属性

1. **对账穷尽：** 一批次匹配后，该分类该账单日全部待对账平台记录与全部导入渠道行均落在恰好一条差异/匹配项上。
   - **类型：** 不变量　**测试策略：** 构造双方各有匹配、仅平台、仅渠道、金额不等四类样本，断言无遗漏无双计。
2. **对账补发不重复到账：** 对同一差异执行补发/履约重试任意次，用户侧 `ARRIVED` 履约至多一次，库存按规则只扣一次。**补发成功后重放原单 `fulfillmentRef` 的到账回调不得把原单打成 `ARRIVED`。**
   - **类型：** 不变量　**测试策略：** 重复点补发与履约重试，断言幂等；补发后再投原渠道回执，原单保持 `FULFILL_FAILED`+`MANUAL`，仅新单可 `ARRIVED`。
3. **补发门禁：** `reviewStatus ≠ CONFIRMED` 的须核渠项上，`REFULFILL` / `MANUAL_GRANT` 一律拒绝且发放表/库存无变化；任何 `AUTO` 路径不得产生 `MANUAL_GRANT`。
   - **类型：** 不变量　**测试策略：** 超时项未核渠点补发/履约重试均 400；开 AUTO 开关跑匹配，无新发放记录。

### 需求 25：风控名单体系

**用户故事：** 作为风控人员，我希望维护用户/IP/设备维度的黑白名单，以便快速拦截已知风险并豁免可信账号。

#### 验收标准

1. 名单维度：用户 ID、IP、设备标识；名单类型：黑名单（拦截）、白名单（豁免风控规则，不豁免认证）。
2. 名单条目属性：名单值、原因、生效时间、过期时间（永久或限期）、操作人、备注。**唯一键 =（维度， 名单类型， 名单值）；同一值在黑、白名单可各存在一条（判定按第 6 条黑名单优先）；重复添加幂等返回既有条目并提示。**
3. 管理动作：单个新增、批量导入（文本/文件，含格式校验与结果报告，权限 `risk:blacklist:import`）、移除（必填移除原因，留痕）；按维度/类型/值/时间的分页查询。
4. 拦截语义分级可配置：**用户黑名单**默认"禁止参与任务与奖励"（任务列表返回空 R13.1、领取拒绝、**进行中实例冻结推进——点击/进度/回调全部推进入口返回"账号受限"（回调返回可重试类结构化错误），实例保持原状态，解除黑名单后调用方按 at-least-once 重投即可继续，平台不缓存冻结期上报**、发放拒绝、登录不拦）；可按名单条目指定"同时禁止登录"（登录即拒）。**IP 黑名单与设备黑名单拦截注册与登录（登录/注册时同步校验 IP 与设备标识）；设备黑名单不影响已登录用户的业务操作。**
5. 白名单账号跳过 R26 风控规则校验，但仍受产品规则（限领、库存、互斥）约束。
6. 优先级：同一主体同时命中黑白名单时，黑名单生效（安全优先）。
7. 判定点：注册/登录（IP、设备黑名单）；领取任务、发奖（用户黑名单 + R26 规则）；**步骤推进入口只做用户黑名单冻结（R25.4），不跑 R26 规则。**
8. 名单全部变更记录审计；命中落风控命中记录（R27）。

#### 正确性属性

1. **名单判定确定性与优先级：** 同一主体名单判定结果恒定；同时命中黑白名单时恒为拒绝。
   - **类型：** 不变量　**测试策略：** 随机名单组合，判定结果与规则一致。
2. **名单时效性：** 过期名单条目不再产生拦截（判定时按当前时间过滤）。
   - **类型：** 不变量　**测试策略：** 时间操纵：条目过期后行为恢复。

### 需求 26：风控规则引擎

**用户故事：** 作为风控人员，我希望配置频率、关联与行为类风控规则，以便自动拦截脚本与批量薅羊毛行为。

#### 验收标准

1. 内置规则集（可启停，阈值与时间窗口可配置，**默认值与合法范围见附录 A**）：
   - R-a 单用户单位时间任务完成数上限
   - R-b 单用户单位时间奖励获得次数上限（全局维度，区别于单奖品限领）
   - R-c 同 IP 时间窗内关联不同账号数上限
   - R-d 同设备标识时间窗内关联不同账号数上限
   - R-e 任务完成耗时低于阈值（防瞬时完成脚本）。**R-e 不是滑窗计数，不写 `risk:cnt`，`window_seconds` 为空。** 只在 GRANT（发奖前）判定；CLAIM / 注册 / 登录 / 步骤推进入口 **不跑 R-e**。时长 `elapsedSeconds = floor((now - 关联任务实例 started_at) 的秒数)`，由调用方传入风控端口。**必须跳过、不命中：**（1）`grantSource != TASK_STEP`（补发 / 签到 / 活动不跑 R-e）；（2）`simulated=true`（模拟器即使 grantSource=TASK_STEP 也不跑 R-e）；（3）实例在**本请求内新建**并经 enter 级联到达 REWARD（纯发奖/领取即发，避免合法秒发被误拦）。**生效条件：** 本请求是 click / callback / progress 触发的级联 GRANT（实例在本请求前已存在）。比较：`elapsedSeconds < threshold`（附录 A `risk.rule.task-complete-min-seconds`，默认 5）→ 按该规则配置的 action 命中。拒绝则发放零副作用（同 R18.7 / 本需求正确性属性 2）。
   - R-f 同 IP 单位时间领取/发奖请求量上限
2. 规则配置项：启用状态、阈值、时间窗口、命中动作（拒绝并提示 / 静默拒绝 / 仅标记观察，**标记观察 = 仅落命中记录并计入统计，不拦截业务**）。**全部频率/关联类规则（R-a~R-d、R-f）统一滑动窗口语义：窗口 = 当前时刻向前 N 秒；R-c/R-d 的"关联"定义 = 时间窗内同 IP（或同设备标识）下出现过登录或注册成功的不同账号数。R-f 只计通过认证与账号状态校验后、到达风控校验点的领取/发奖请求，被更早环节拒绝的请求不计数。R-e 无时间窗口、不写 `risk:cnt`（见第 1 条 R-e）。**
3. 执行点与同步性：R26 规则只在**领取任务前、发奖前**同步执行（拒绝则动作不发生）。**R-e 仅在发奖前（GRANT）且满足第 1 条 R-e 生效条件时判定，领取任务前不跑 R-e。** 注册/登录只跑 IP/设备名单（R25），不跑 R-a–R-f。步骤推进入口只跑用户黑名单冻结（R25.4），不跑 R26；级联 GRANT 属发奖前，跑 R26（R-e 按第 1 条生效/跳过条件）。规则系统异常时按可配置策略降级（默认放行并落降级事件 + 告警）。
4. 每次命中落风控命中记录（唯一事实源）：规则编码、维度值、用户、上下文快照、命中值与阈值、处置结果、时间；同时异步生成埋点侧投影事件（R28）。
5. 风控校验对主链路的性能开销：领取/发奖接口 P95 增量 ≤ 20ms。
6. 规则配置变更实时生效并审计（权限 `risk:rule:config`）。
7. P1 扩展方向（本期不实现）：风险评分模型、行为序列异常检测、设备指纹强化、命中阈值自动加黑。

#### 正确性属性

1. **规则判定确定性：** 相同输入（用户行为统计 + 规则配置）判定结果恒定。
   - **类型：** 不变量　**测试策略：** 随机行为序列重放，两次判定一致。
2. **拒绝零副作用：** 被规则拒绝的领取/发放不产生实例、发放记录或库存变化；重复请求结果一致并各自记录命中。
   - **类型：** 不变量　**测试策略：** 并发重放被拒请求，业务表无变化、命中记录数与请求数一致。
3. **降级可观测：** 规则系统异常时的降级决策全部留痕（降级事件计数）。
   - **类型：** 后置条件　**测试策略：** 故障注入，断言放行 + 降级记录。
4. **R-e 判定范围：** 同请求新建并级联发奖不跑 R-e；已存在实例被推进至 REWARD 且 elapsed < 阈值则按 action 拦截且零副作用。
   - **类型：** 不变量　**测试策略：** 领取即发路径不落 R-e 命中；先领取后推进至 REWARD 且耗时不足则拒绝且发放零副作用。

### 模块 F：埋点与数据采集（P0 基础）

### 需求 28：统一事件模型与上报

**用户故事：** 作为运营人员，我希望用户行为与系统业务动作被统一采集，以便后续分析与风控统计有完整数据。

#### 验收标准

1. 统一事件模型：每条事件包含 Who（用户 ID，匿名时设备标识）、When（客户端触发时间 + 服务端接收时间）、What（事件编码 + 事件属性 JSON）、Where（平台端标识、App/页面版本、IP）。
2. 事件编码规范 `<域>.<对象>.<动作>`，如 `page.view`、`task.card.exposure`、`task.instance.complete`、`ad.carousel.click`；服务端事件（注册/登录成功、实例开始/步骤完成/实例完成/放弃/过期、发放成功/失败、履约到账/失败、风控命中投影）与客户端事件进入同一事件存储，以来源字段区分（client/server）。全集见附录 D。
3. 上报端点 `/api/common/track/batch`：单批 ≤ 50 条、单条 payload ≤ 8KB（附录 A）；支持登录与匿名（设备标识）两种上报身份；接口独立限流（附录 A）。
4. 每次上报携带公共属性（platform、appVersion、deviceId），事件私有属性按事件元数据约束。
5. 上报成功返回接收条数；畸形事件（超限、非法 JSON、超长）丢弃并计入丢弃指标，不影响同批合法事件接收。
6. 未登记事件默认接受并标记 unregistered；策略可配置为拒绝（附录 A）。
7. 事件一旦接收只增不改不删；分析口径以服务端接收时间为准，客户端时间仅作参考。
8. 埋点上报链路故障不影响任何业务功能；上报端点独立降级（限流/丢弃）并输出丢弃率指标。
9. 服务端事件经 Outbox 异步写入（业务事务不受影响）；**客户端事件按下发批次合并为单行存储：行级字段 = 公共属性 + 批次接收时间，行内 `events` 为 JSON 数组（每元素 = 事件编码 + 事件属性 + 客户端触发时间）；查询接口透明展开。**
10. 客户端上报行为规范（约束门户前端）：本地聚合（满 20 条或 5 秒触发）、失败重试 ≤ 2 次、上报绝不阻塞页面与业务交互。
11. 首版不做匿名 deviceId 与登录 userId 的事件身份归因打通（范围声明），P1 评估。
12. **首版代码埋点点位基线：** 逐点位的**事件编码、来源、私有属性以附录 D 事件编码基线表为封闭契约**；全部事件编码登记入 R29 元数据种子并随版本交付。
13. **通用曝光判定口径（任务卡片等内容元素）：** 元素进入可视区域 ≥ 50% 且持续 ≥ 500ms 计一次有效曝光；同一页面会话（页面未重新加载期间）内同元素只计一次。（广告素材曝光按 R30.12 专用口径——渲染即计，两者差异为有意设计：广告投放统计采用更宽口径；均为客户端固定规范值，不做服务端配置。）
14. **页面停留：** 路由切换或页面卸载时上报页面离开事件（含停留秒数）；页面卸载场景优先使用浏览器 sendBeacon 直发，无法直发时本地暂存并于下次访问首屏补发（补发事件按实际到达时间入库，分析口径以服务端接收时间为准，R28.7）。

#### 正确性属性

1. **业务非阻塞不变量：** 上报端点完全不可用时，全部业务功能（登录/任务/领取/发奖）行为不变。
   - **类型：** 不变量　**测试策略：** 故障注入上报端点，业务链路全绿。
2. **事件不可变性：** 已接收事件不可被任何在线请求修改或删除（无删改 API）。保留期满的归档/清理属运维调度（`retention.event-days`），不提供在线删改入口。
   - **类型：** 不变量　**测试策略：** 无篡改/删除服务方法（架构测试）；清理任务只删过期分区。

### 需求 34：任务浏览与参与体验

**用户故事：** 作为 C 端用户，我希望清晰看到任务进度并顺畅完成步骤，随时知道下一步做什么。

## 非功能性需求

### 性能

1. 门户任务列表接口在 500 QPS 压力下（portal-app 2 实例），P95 ≤ 300 ms。
2. 步骤推进与 internal 回调在 300 QPS 下，P95 ≤ 200 ms。
3. 含发奖的任务完成事务 P95 ≤ 500 ms。
4. 风控校验对领取/发奖接口的 P95 增量 ≤ 20 ms。
5. 埋点上报端点集群吞吐 ≥ 6000 events/s（容量假设峰值的 2 倍余量），P95 ≤ 100 ms；除限流与丢弃策略外丢弃率 < 0.1% 且可观测。
6. 广告位拉取接口 P95 ≤ 100 ms @ 300 QPS（P1）。
7. 后台管理与列表查询 P95 ≤ 800 ms。
8. 容量设计假设：门户用户 100 万、日活 10 万、日新增任务实例 50 万、日事件量 500 万（峰值 3000 events/s，事件表按月分区）。

### 可用性

1. 门户与管理应用可用性 99.9% 为**运营目标**，不是 P0 验收门禁。P0 验收 = R31 部署编排可重复 + 健康检查 + NFR 性能 1–5 与 7 的 k6 门槛（性能 6/8 属 P1/容量复验）。
2. portal-app 无状态，支持水平扩展与滚动发布。
3. 定时任务多实例部署下恰一实例执行（分布式锁）。
4. 降级策略明确：Redis 故障时会话不可用（拒绝请求，不静默放行）；限流器故障放行并告警（fail-open）；缓存故障回源数据库；埋点端点过载按丢弃策略降级；风控规则系统异常按可配置策略降级（默认放行 + 降级事件留痕 + 告警）。

### 可观测性

1. 指标暴露：应用技术指标（HTTP QPS/错误率/P95、连接池、Redis 命令延迟）与业务指标（发奖量与失败率、Outbox 积压量、限流触发次数、埋点丢弃率、库存水位、风控拦截量、降级事件计数、审计写入延迟）。
2. 日志：结构化 JSON 输出，traceId 贯穿 admin-app 与 portal-app 全链路。
3. 告警项基线：HTTP 错误率/P95 超阈值、Outbox 积压超阈值、发放永久失败发生、任一奖品库存 ≤ 总量 10%、Redis 故障/切换、降级事件发生、埋点丢弃率 > 0.1%。
4. 两应用均提供健康检查端点（存活/就绪）。

### 安全

1. 全部对外通信 TLS 1.2+；后台 Cookie HttpOnly + SameSite=Strict。
2. 密钥（数据库、Redis、会话、internal 签名密钥）仅环境变量注入，仓库与配置文件无明文。
3. 不存在任何可关闭鉴权的全局开关；调试免登仅本地 profile 且生产 profile 编译期排除。
4. 全部输入校验（Bean Validation）+ 参数化 SQL；后台写操作 CSRF 防护。
5. 登录类接口：验证码 + 失败锁定 + 双维度限流；埋点匿名端点：独立限流 + payload 上限 + 无内容回显；internal API：调用方登记 + HMAC 签名防重放。
6. 生产环境关闭 API 文档 UI 与 actuator 敏感端点；CORS 白名单经配置管理。
7. 审计与事件日志敏感字段落库前脱敏；设备标识不作为鉴权依据。
8. 遵循 OWASP Top 10 防护基线。

### 可扩展性（架构）

1. 业务领域按 Maven 模块物理隔离（P0：identity / task / reward / risk / tracking；P1：signin / activity / ad），依赖单向，编译期与 CI 强制。积分在 reward 模块内。
2. 跨领域调用仅两种形式：同步端口接口（同库同事务）与领域事件（Outbox）；禁止跨领域直接访问对方数据表。
3. admin-app 与 portal-app 独立部署、独立扩容、独立发布；接口命名空间按 §简介 规划（`/admin`、`/api/common/<模块>`、预留 `/api/<module>`、`/internal`），网关按前缀静态路由，新增独立模块集群不改既有路由。
4. 共享数据库初期单实例 MySQL，表按域前缀组织，预留按域拆库。
5. **架构红线：portal-app 必须装配 task 与 reward**（积分在 reward 内），保证 REWARD 发放与步骤推进同 JVM 同事务（R14.5/R18.1 语义前提）；拆分为独立进程属重大架构变更，需先行评审 Outbox/Saga 替代方案。

### 可维护性

1. 数据库结构变更仅经版本化迁移脚本，已应用脚本不得修改。
2. API 契约以 OpenAPI 为准随 CI 导出；前端类型自动生成，禁止手写重复类型。
3. 编码规范以静态检查在 CI 强制；测试与构建不依赖外部手工环境（数据库/缓存经容器化测试依赖提供）。
4. 关键并发与幂等路径（实例创建、步骤推进、发奖、领取、积分、库存、活动限量、广告频控、名单判定）具备基于属性的测试覆盖。

### 数据与合规

1. 用户信息收集最小化；逻辑删除后个人信息不再对外展示。
2. 审计日志保留 ≥ 180 天，事件日志保留 ≥ 90 天，指标聚合表保留 ≥ 1 年，到期归档或清理策略经系统配置管理。
3. 埋点数据仅用于产品分析与风控统计，不含明文密码、令牌、密钥等敏感字段。

## 附录 C：全局接口契约

> 适用于全部命名空间（/admin、/api/common、/api/<module>、/internal）。

**统一响应体**

- 成功：`{ "code": 0, "message": "ok", "data": <业务数据>, "traceId": "<追踪标识>" }`
- 失败：`{ "code": "<业务错误码>", "message": "<可展示文案>", "traceId": "<追踪标识>" }`；业务错误码格式 `<域>.<场景>.<原因>`（如 `task.claim.mutex-blocked`、`auth.login.locked`）。

**HTTP 状态码映射**

| 场景 | HTTP |
|------|------|
| 成功 | 200 |
| 参数非法 / 通用业务规则拒绝 | 400 + 业务错误码 |
| 未认证 / 会话失效 | 401（含会话失效原因码） |
| 无权限 | 403 |
| 资源不存在 | 404 |
| 账号锁定 | 423 |
| 触发限流 | 429 + Retry-After |
| 服务端异常 | 500（对外文案统一，traceId 关联内部日志） |

**分页契约**

请求参数 `page`（从 1 起）+ `pageSize`（默认 20，上限 100，超出按 100 截断）；响应统一 `{ total, records }`。

**时间基线**

数据库与服务内部统一 UTC 存储；对外接口时间字段一律 ISO-8601 带时区偏移；业务口径（cycleKey 生成、一切"每日/当日"计数窗口、自然日切分）统一 UTC+8 自然日 `[00:00:00, 24:00:00)`。

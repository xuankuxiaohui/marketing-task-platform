# 可行性分析：任务步骤推进引擎

> 对象：requirements.md R14 / R12 / R15 / R18。场景矩阵 **24 行**（与 design §7.5 一致）。
> 发放可重试失败：REQUIRES_NEW 留痕后再回滚主事务（design §5.6.2）。
> 姊妹矩阵：[feasibility-recon.md](feasibility-recon.md)（R37）· [feasibility-risk.md](feasibility-risk.md)（R25/R26）。

## 1. 结论摘要

**可行。** 五类步骤 × 四入口 × 并发 / 重复 / 异常均有可实现方案。正确性依赖：数据库唯一约束幂等、行级乐观锁并发收敛、版本快照隔离。配套约束见 §6：任务步骤数上限 50、进度去重表语义、累加冲突重试、portal-app 装配 task 与 reward 以维持同事务发放。

## 3. 关键机制论证

### 3.1 并发收敛：乐观锁 + 唯一约束双保险

portal-app 无状态多实例部署下，同实例并发推进的竞争全部收敛到 MySQL 单行：

```sql
UPDATE task_instance_step SET status='COMPLETED', completed_at=NOW(), version=version+1
 WHERE id=? AND version=? AND status='ACTIVE';
-- 影响行数 = 0 → 冲突：重读行，若 COMPLETED → 幂等返回；若仍 ACTIVE（他事务未提交）→ 短暂自旋重试（上限 3 次）
```

- 同一步骤的两个并发完成请求：恰一个影响行数为 1，另一个走幂等/重试路径 —— exactly-once 由 DB 行锁串行化保证，与应用实例数无关。
- 发放幂等独立于步骤锁：`rwd_record.uk_idempotent` 唯一约束，即使乐观锁实现有 bug 也不会二次发放 —— 资金安全有第二道防线。
- 实例终态保护：实例状态变更为 COMPLETED/EXPIRED/ABANDONED 均为 CAS 更新，与推进事务在同一连接内，无窗口。

**结论：正确性仅依赖数据库 ACID，多实例/虚拟线程/应用重启均不破坏。**

### 3.2 级联深度与事务时长

最坏情况：领取后一次事务级联推进 N 个 PASSIVE/REWARD 步骤。每次级联 = 1 次行 UPDATE +（REWARD 时）1 次发放插入。事务内无外部 IO（发放为进程内端口调用、分支求值为内存计算、快照取自缓存）。

- 单次行 UPDATE（索引命中、行锁无竞争）耗时量级 ~0.1–1ms；50 步级联事务估算 < 100ms，远低于 500ms NFR。
- **约束：任务步骤数上限 50**（`task.step.max-count`，R11.2）；无上限的万步任务会产生长事务 + 快照膨胀。
- 事务重试路径（发放可重试失败后人工重试）：重试入口从"步骤仍 ACTIVE"处重新进入级联，无需记忆中间态 —— 天然可重入。

### 3.3 PROGRESS 并发累加与 reportId 去重

- 去重存储选 **DB 唯一约束**（进度去重表 `(instance_id, step_id, report_id)` 唯一键）：与累加事务同库同事务，崩溃安全、无需引入 Redis 事务复杂性。写入量评估：进度上报峰值按 internal 限流 200 QPS/accessKey 计，日均 < 500 万行，按月分区与事件表同策略，可行。Redis SETNX 方案被否决：与累加非原子，崩溃窗口会丢去重记录。
- 累加冲突重试：两个不同 reportId 并发累加，乐观锁败者重读新值再累加（携带原 delta），重试 ≤ 3 次；耗尽后返回「处理中」业务码（外部系统按 at-least-once 语义重投，reportId 去重保证不重复累加，R15.4）。
- 单次上报 value ∈ [1, 1000]（R11.2）；一次上报即达标仅当 `value ≥ progress_target` 且 target ≤ 1000 时成立。更大目标必须多次上报累加。刷量风险由单次上限 + R26 R-f（IP 频率）+ accessKey 限流约束。

### 3.4 发放同事务的架构前提

R18 要求 REWARD 发放与步骤完成同事务。成立的前提是发放代码与步骤引擎**同 JVM 内**（同线程同事务传播）：

- portal-app 装配 task 与 reward（积分在 reward 内）→ `RewardPort` 与积分入账为进程内 Bean，事务传播 REQUIRED 自然合并 —— **架构红线：portal-app 必须装配 task 与 reward，禁止拆成独立进程**（拆分需先重构为 Outbox/Saga，属重大架构变更）。
- admin-app 模拟测试复用同一引擎服务（进程内）→ 行为与 C 端一致，R24 可行。
- 未来 `/api/<module>` 独立模块若需发奖，通过 internal API 调 portal 的发放能力或引入 Saga —— 超出本期，风险已隔离在拆分决策点。

### 3.5 分支求值性能

- 表达式在任务保存时编译校验并缓存（编译产物随快照存储）；运行时求值为纯内存布尔计算，AviatorScript 典型表达式 P99 < 1ms（Spike T2 验证项）。
- 快照读取走两级缓存（任务快照命名空间），命中后实例步骤渲染与分支求值零 DB 读。
- 求值上下文（FilterContext/BranchContext）为显式参数对象，无 ThreadLocal —— 虚拟线程安全。

### 3.6 风控同步插入

领取/发放链路的风控检查为 Redis 计数器读取 + 名单缓存判定，O(1) 且无 DB 访问；20ms P95 增量预算充足。风控降级放行（R26.3）保证风控故障不阻塞主链路。

### 3.7 容量推演

- 推进/回调 300 QPS：每请求 1–3 次行 UPDATE + 1 次快照缓存读；MySQL 单实例数千 QPS 单行更新能力下余量 > 5 倍。
- 连接池：2 实例 × 20 连接，事务平均 < 50ms（含发奖），连接持有时间短，虚拟线程下无池耗尽风险（事务内无外部 IO 是前提，已在红线中约束）。
- 热点行风险：同一实例并发推进才会同行竞争，单用户自身操作天然低并发；无全表级热点。

## 4. 被否决的备选方案（记录决策依据）

| 备选 | 否决原因 |
|------|----------|
| 分布式锁（Redisson）保护步骤推进 | 正确性可满足，但引入锁超时/续期/宕机释放等复杂度；行级乐观锁在 DB 层天然串行，无额外组件依赖。锁仅用于奖品领取（R19）等无唯一约束可依托的场景 |
| Redis SETNX 做 reportId 去重 | 与累加操作非原子，崩溃窗口丢失去重记录 → 重复累加；DB 唯一约束与事务一致 |
| 发放异步化（Outbox 事后发放） | 违反 R14.5"发放失败步骤不推进"语义，用户完成却可能漏奖需补偿；同步事务在容量推演下可行，无必要引入异步复杂性 |
| 状态机框架（Spring Statemachine） | 步骤状态仅 4 态 3 迁移，显式条件 + CAS 足够，框架引入的抽象成本大于收益 |

## 5. 残余风险

| 风险 | 等级 | 缓解 |
|------|------|------|
| 级联事务遇慢 SQL（锁等待）拖长事务 | 中 | 推进路径 SQL 全部索引命中（设计阶段执行计划审查）；压测任务 43/49 覆盖推进场景 |
| 外部回调方不传 reportId 或复用 reportId | 中 | internal 契约文档 + 联调校验；reportId 缺失直接拒绝（参数非法） |
| 快照 JSON 过大（50 步 + 平台动作 ×5 端） | 低 | 快照体积估算 < 100KB；缓存与 DB 均无压力；任务编辑器前端提示规模 |

## 6. 需求约束

1. **R11.2 / 附录 A**：任务步骤数上限 `task.step.max-count` 默认 50（级联事务时长上界）；首步骤为 REWARD（纯发奖任务）为合法配置。
2. **R14.3 / R15.1**：进度去重按（实例, 步骤, report_id）数据库唯一约束；去重记录与进度累加同事务。
3. **R14.3 / R15.4**：累加冲突自动重试 ≤ 3 次，耗尽返回「处理中」业务码；外部系统按 at-least-once 重投，由 reportId 去重兜底。
4. **NFR 可扩展性 5**：portal-app 必须装配 task 与 reward（积分在 reward 内），保证 REWARD 发放与步骤推进同事务；拆成独立进程属重大架构变更。

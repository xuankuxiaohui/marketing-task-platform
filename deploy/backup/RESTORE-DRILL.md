# 备份恢复演练

依据 R31.3，最终需要全量备份、连续 binlog 归档和指定时间点恢复。项目未上线；**现有脚本尚不能视为经过验证的恢复方案**。本轮仅静态审阅，没有执行备份或恢复。

## 当前实现缺口

| 入口 | 已有行为 | 待修复 / 验证 |
|---|---|---|
| [backup.sh](backup.sh) | 生成带 `--master-data=2` 坐标的全量备份，复制当时可见的 binlog，生成校验文件 | 一次文件复制不等于连续归档；复制错误被忽略，活动 binlog 的完整性需验证 |
| [restore.sh](restore.sh) | 先导入全量，再按文件名重放全部 `mysql-bin.*`，可设置停止时间 | 没有读取全量备份的 binlog 起始坐标，可能重复回放备份已包含的数据；未校验归档完整性和校验文件 |

这些问题应在代码阶段独立修复。当前恢复命令直接写目标数据库，必须先具备目标隔离、起点选择、完整性校验和失败处理，再执行下述演练。Redis 会话不依赖备份恢复，缓存应可重建。

## 演练设计

1. 准备与源库隔离的恢复实例，记录源库/目标库、版本、时区与备份保留策略；确认不会覆盖开发共享库或其他项目数据。
2. 在时间点 `T0` 取得完整备份并记录 binlog 文件与位置；此后持续归档 binlog。
3. 写入标记 A，选定目标时间 `T`，再写入标记 B。记录准确时间与提交顺序，保证 `T0 < A < T < B`。
4. 选择 **早于 T** 的全量备份，校验文件及完整归档链。还原全量后，从其记录的坐标回放到 T，而不是从第一份 binlog 开头重放。
5. 验证 A 存在、B 不存在，并核对任务实例、发奖记录、积分余额与流水的一致性。不得只检查数据库能启动。
6. 启动应用验证关键查询/业务流程，记录恢复耗时与丢失窗口，对照规格要求验收。

全量备份若晚于 T，之后再设置 binlog 停止时间不能撤销全量里已有的数据。原流程“在目标时间之后再备份并恢复到目标时间”不再作为演练方法。

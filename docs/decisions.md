## DEC-001：代码与功能基线

**本批已明确**：用户授权继续到完成一个较大的功能。以当前 `dd9feba` 加既有未提交工作区作为门户个人中心批次 R5-01 的实施基线，保留已有功能和文档改动，不切到旧主干、不混入提交。需编辑的既有列表文件在本批开始时保存了临时快照。R5-01 只调整前端列表、详情和相应会话隔离，测试与相关说明同批交付；后端、Schema、依赖与 API 契约不变。本结论仅覆盖本批，不授权自动推进全部路线或清理环境数据。

**当时事实**：工作区基于 `feat/portal-guest-home-ux` 的 `dd9feba`，本地 `origin/master` 为 `745485a`，且有未提交的门户、活动、奖品来源与契约改动。当时未核验远端最新状态；新任务重新检查 Git 状态。

**建议**：以当前工作区作为功能盘点输入；正式实施前为已有改动建立可恢复快照或独立提交，核实主干与前置分支关系，再建立隔离的重构分支。不要直接从旧主干重写而遗漏现有功能，也不要把混合工作区一次性提交为重构。

历史背景：旧 design §7.9 笼统描述“匿名访问业务页 → 重定向登录”，而旧 R32.1 / design-api §4.9.0 已列出允许匿名的活动和任务浏览。后续实施仍需逐路由区分公开浏览与受保护操作，不能按旧旅程表述回退游客功能；体验确认见 DEC-008。

**关闭条件**：记录实施 commit、保留/放弃功能清单、未提交改动的归属与前置分支关系。文档整理不依赖本项关闭。

## DEC-002：Outbox 消费容量

**依据**：历史 design-architecture §6.4 写每 5 秒取最多 100 条；当时核对的 [OutboxRelay](../server/platform-infra/src/main/java/com/mkt/infra/outbox/OutboxRelay.java) 每 tick 只处理一批，[InfraAutoConfiguration](../server/platform-infra/src/main/java/com/mkt/infra/InfraAutoConfiguration.java) 使用 5000 ms fixedDelay。旧性能条款的推进/回调 300 QPS 只保留为背景，当前目标按 DEC-006 重新确认；业务成功仍需可靠投递事件。

**问题**：单 relay 忽略处理时间的预算约 20 events/s，与持续有效写入产生的事件量不匹配。多节点调度会改变总预算，不能把此值当集群实测上限；仍需明确可持续消费与故障恢复的设计。

**建议**：保留 producer 隔离、同事务 append、锁与幂等；一次持锁期间在有限时间预算内处理多批，空队列退出、预算耗尽让出。批大小、间隔和时间预算通过压测确定。

**关闭条件**：记录消费预算、多节点公平性、重试与停机行为；测试稳态积压、最老事件延迟、重投和恢复排空。不先添加 MQ 或擅自更改事件全集。

## DEC-003：跨域只读契约与人群能力

**依据**：领域间禁止互访表的边界保留在 [AGENTS](../AGENTS.md)。旧设计 §2.2.3 / §3.11 和需求 R22.3、R30.3/6 曾描述只读端口、活动与广告的人群复用能力；具体缺口和候选方案如下，实施前确认本次所需行为。

**缺口**：当前 `platform-contract` 没有人群查询端口。广告 `AdPortalAppService.visible` 没有使用登录用户的人群配置；活动 `ParticipationRules.firstReject` 把人群码当成配置开关，最终只检查直接用户名单。管理应用的指标和模拟服务也直接查询多域表；设计 §3.11.3 本身允许 admin-app 聚合扫描，因此应先明确聚合例外与一般查询的边界，不能将这些 SQL 一概判定为违反 RL-03。仅搬动类或新增一个泛化查询工具不能解决归属问题。

**建议**：先列出人群、奖品来源、用户汇总、看板与模拟各自需要的最小读模型；由数据拥有域提供有界批量查询，通过 contract 组合。纯规则求值与数据库准备分离。新增接口同批记录名称、归属、空值及失效语义，不从旧草案直接推断已有接口。

**关闭条件**：契约覆盖独立人群包、直接名单、组合条件及匿名边界；行为回归可区分允许/拒绝；扩展跨域 SQL 检查范围。不能把旧 STATUS 的“CrowdPort”误认为已存在接口。

## DEC-004：独立事务与失败审计语义

这是三项需要分别核对的边界，不得统一用 `REQUIRES_NEW` 解决：

| 项目 | 两方依据或待澄清处 | 需要明确 |
|---|---|---|
| 永久发奖失败留痕 | 旧 design-algorithm §5.6.2 只将可重试失败列为同事务例外；[GrantFailureLedger.markPermanent](../server/domain-reward/src/main/java/com/mkt/reward/application/GrantFailureLedger.java) 在已有主事务时也开启独立事务 | 永久失败记录是否应随父级联回滚；父事务后续失败时预期状态与事件 |
| 积分过期调度 | 已删除的 05-security §3 曾限定两处独立事务；[PointsAppService.expireDue](../server/domain-reward/src/main/java/com/mkt/reward/application/PointsAppService.java) 按笔开启独立事务 | 调度批次与单笔业务事务的范围；该路径不是 earn 独立提交，不应误报正常发奖失去原子性 |
| 失败审计 | 旧 requirements R1/R2 要求失败登录与未授权留痕；R10 属性 1 同时写“与操作成败无关”和“事务回滚则无记录”；旧 design §6.5 要求异常记 FAILURE，§7.3 又要求随机失败序列逐条对应 | 区分鉴权拒绝、未进入业务事务的失败、业务返回失败、业务事务回滚；每类是否留痕、事务归属和去重方式 |

**建议**：先形成失败类型 × 业务状态 × 审计/事件记录的期望表，对照实现和回归核验，确认存在冲突后才修订文字。审计条款中的回滚例外已存在，因此不能简单断言“所有失败都必须另开事务”。当前后台登录通过提交失败结果后再由 Controller 抛错、鉴权拒绝通过独立于业务请求的 REQUIRED 事务留痕，已有可兼容这些要求的实现；本项要求补全失败分类，不预判现有路径错误。


**已核实的实现间隙**：[TaskDefinitionAdminController](../server/domain-task/src/main/java/com/mkt/task/controller/admin/TaskDefinitionAdminController.java) 的 save/copy 在控制器标注审计，应用服务先提交业务事务，[AuditedAspect](../server/domain-identity/src/main/java/com/mkt/identity/audit/AuditedAspect.java) 返回后才在无外层事务时另开事务追加审计 Outbox。这存在业务与审计分开提交的窗口，需要真实 Spring/MySQL 回归核验 R10.3 的保证。现有 [AuditCompletenessIT](../server/domain-identity/src/test/java/com/mkt/identity/AuditCompletenessIT.java) 的十个失败样本只有失败登录与 forbidden，尚不能证明参数非法、唯一冲突和业务回滚路径的完整性。

**关闭条件**：明确决定、实现与真实数据库事务测试采用同一张行为表；失败不会产生重复发奖、额外扣分、丢失必要留痕或重复审计。

## DEC-006：性能目标及证据口径

Kiro 规格退役后，旧 requirements NFR、design §7.8 和脚本中的阈值均不直接视为本轮已确认目标。旧重构草案还记载了“单实例读取 1000 次/秒、写入 200 次/秒”，但没有独立确认该记录的来源、接口范围或资源预算；这些数字仅保留为候选背景，不当作已批准的新门禁。本次文档清理不修改已有脚本阈值。

开始性能改造前明确机器规格、实例数、连接池、数据规模、冷热缓存、热点比例、有效业务成功率与压测时长；分别计量请求数、成功状态变更数和接收事件数。不能以终态幂等返回、空数据快响应或测试方法存在证明达标。

**关闭条件**：在本决策记录确认目标口径，同步压测配置与验收说明；按 [性能验证说明](../perf/README.md) 留存可复现报告。没有报告时只能陈述静态风险，不能承诺容量。

## DEC-007：任务旧实例、下线与到期优先级（已确定）

2026-10-07，用户明确选择推荐规则，用于生命周期批次 R2-01。原冲突为 R12.2 快照隔离与 §5.5 编辑态组查询不一致、R14.10 重发语句未区分新旧实例，以及 EXPIRED 拒绝与终态完成步骤幂等描述重叠。

| 边界 | 最终规则 |
|---|---|
| 旧实例归属 | 固定领取时绑定的快照与互斥组编码；组的 crossCycle 仍使用当前配置，按原规则比较 cycleKey |
| 下线期限 | 对未到期的 IN_PROGRESS 实例，用绑定快照、冻结的 cycleKey、本次下线时刻与当前 N 重算；无窗一次性任务允许延长；已到期或终态不复活 |
| 重新发布 | 清除定义本轮 offlineAt；仅新实例使用新发布配置，旧快照、周期键与已计算期限保持原值 |
| 过期优先 | EXPIRED 或在途到期拒绝推进，包括重投和未运行扫描的场景；COMPLETED 保留合法入口及已接受进度报告的既有幂等范围 |
| 并发与时间 | 领取定义共享锁后锁用户；所有定义写入先持排他锁；推进/终态持实例锁，每次状态写入前重新检查 Clock，仅 CAS 获胜者写事件与级联 |
| 奖励重试恢复 | 到期不恢复任务，保留已成功发放权益；锁后重读步骤，不用旧 ACTIVE 对象越过后续步骤 |

当时已落实到实现与回归，并同步了旧需求 v3.11、设计 v2.17；旧规格退役后以上决定继续保留。表结构、依赖、HTTP 契约、事件与错误码未新增；旧规范中过宽的 FOR UPDATE 句子当时已收窄为用户表限制。2026-10-07 的真实 MySQL 执行结果见 [核验报告](full-flow-verification-2026-10-07.md)。
